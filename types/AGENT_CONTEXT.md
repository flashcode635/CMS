# Directory: types

Primary Purpose: Global frontend/domain type definitions in a single barrel file (`index.ts`). These are hand-written UI shapes, **not** derived from the database — only `TeamMember` is currently imported anywhere, and `Admin` has its own interface in `lib/models/Admin.ts` (`IAdmin`), which is intentionally separate.

> Dependencies/Consumers/Runtime lines are normally regenerated by `npm run graph`. That script is currently missing (see `tools/AGENT_CONTEXT.md`), so this file is maintained by hand.

## Files

### `index.ts`

[index.ts]: 12 exported interfaces describing frontend content models (profile, navigation, blog, team, universities, events, testimonials, contact form, jobs, brochures, country pages). Pure types — no runtime code, no imports, no side effects.

- **Runtime:** shared / type-only. All exports are `interface` declarations, which TypeScript erases: importing this file produces no runtime import, so it is safe in both client and server components.
- **Purpose:** One central vocabulary for view-model shapes used by pages/components, kept independent of persistence documents. Resolved via the tsconfig path alias `@/*` → `./*`, so `import { TeamMember } from "@/types"` reaches `types/index.ts`.
- **Exports & signatures:** 12 named exports, no default export, no `export type` unions, no enums, no constants, no generics:

- **Constants & types:** No runtime constants. Structural conventions worth knowing:
  - IDs are `string | number` in every content interface; `UserProfile.id` is `string` only.
  - Dates/times (`date`, `readTime`, `year`, `fileSize`, `tuitionFee`) are pre-formatted **strings**, not `Date`/numbers.
  - Two interfaces declare string-literal unions: `UserProfile.role` (`'ADMIN' | 'USER' | 'GUEST'`, single quotes, uppercase) and `EventItem.status` (`'upcoming' | 'past' | 'ongoing'`). Everything else is `string`, so field-level validation must happen elsewhere.
  - No props types, no API response envelopes, no `Partial`/`Record` helpers exported here.
- **Error handling:** N/A — types only, erased at build time. No runtime validation (no Zod/valibot), so API/form payloads are unchecked at runtime.
- **Dependencies:** None (file has zero imports). Consumed through the `@/*` alias from `tsconfig.json`.
- **Consumers (verified by grep):** **only** `components/homepage/MeetOurTeam.tsx` — `import { TeamMember } from "@/types";` and `interface CustomTeamMember extends Partial<TeamMember> { name: string; role: string; photo: string }`. Note that `MeetOurTeam` overrides the image field name (`photo` instead of `TeamMember.image`), so the shared type is only used for the optional `bio`/`linkedin`/`id` fields there.
  - Unused (no importer anywhere): `UserProfile`, `NavItem`, `NavCategory`, `BlogAuthor`, `BlogPost`, `University`, `EventItem`, `Testimonial`, `ContactFormData`, `JobOpening`, `BrochureItem`, `CountryInfo`.
  - These shared view types are independent of any authentication or database model.
- **Notes:**
  - Components currently declare their own local data shapes inline (e.g. `collegeCards.tsx`, `Marquee.tsx`, `TestimonialsSection.tsx`) rather than adopting these interfaces — so "global data models" is aspirational; changing a field here is low-risk today (one consumer) but these types are **not** the contract the UI actually uses.
  - Because the file is a barrel, adding a type with the same name as a local interface in a consuming component will silently shadow/conflict; keep names distinctive.
  - No database mirror exists for these interfaces.
